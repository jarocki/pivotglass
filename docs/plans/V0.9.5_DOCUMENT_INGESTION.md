# Pivotglass v0.9.5 document-ingestion plan

**Status:** partially delivered; v0.9.5 candidate boundary frozen

**Original deadline:** complete and release no later than v0.9.5

**Disposition (2026-08-31):** v0.9.5 qualifies bounded local preview for text,
Markdown, HTML, CSV, JSON/JSONL, and RFC 5322 email; deterministic exact-span
entity candidates; immutable internal intake/proposal authorities; hostile-input
tests; and explicit safety/capacity boundaries. It does **not** claim the full
target below. PDF extraction/OCR, Office/images/archives, URL/RSS/batch intake,
persistent browser admission/export/purge, complete review UI/TUI, the shared
SCOT4/Synapse benchmark, and live remote exchange remain v1.0 gates. The
[v0.9.5 quality record](../QA_V0.9.5.md) and [compatibility
matrix](../COMPATIBILITY.md) are the current executable contract; this document
retains the original target for traceability.

**Goal:** turn threat reports, messages, structured feeds, and analyst-provided
documents into reviewable evidence, entities, candidate relationships, gaps,
and pivots while preserving exact provenance. Pivotglass must match or exceed
the relevant SCOT4 and Vertex Synapse capabilities on a shared, published test
corpus rather than by counting features.

## Product boundary

A document is evidence that a source made statements. It is not proof that
those statements are true. Extracted strings are candidate entities. A model's
entity, relationship, behavior, or attribution output is a proposal. None of
these becomes an observed relationship, actor identity, confidence judgment,
or accepted TTP without the existing admission and analyst-review authorities.

Document contents are untrusted data, never instructions to Pivotglass, a
tool, or a configured model.

## External baselines

The initial comparison uses pinned versions and records their exact
configuration:

- [SCOT4 Flair and Entities](https://sandialabs.github.io/scot4-docs/usage/flair/)
  identifies entities in HTML and plain text, records their locations,
  cross-references appearances, supports a core entity catalog and user-defined
  entity classes, and exposes enrichment and pivot context.
- [SCOT4 Threat Intel Workflow](https://sandialabs.github.io/scot4-docs/usage/tiworkflow/)
  accepts raw reporting as dispatches, ingests RSS material, promotes reviewed
  material to Intel and Products, and uses entities to connect appearances.
- [Vertex Synapse Ingest Tool](https://synapse.docs.vertex.link/projects/optic/en/stable/user_interface/userguides/ingest_tool.html)
  ingests URL or uploaded CSV, JSON, and JSONL data through testable Storm and
  recommends testing and running in a forked view before merge.
- [Vertex Synapse scrape library](https://synapse.docs.vertex.link/en/latest/synapse/autodocs/stormtypes_libs.html#lib-scrape)
  extracts normalized node definitions and contextual offsets from text.
- [Vertex Synapse file handling](https://synapse.docs.vertex.link/en/stable/synapse/userguides/storm_ref_type_specific.html#actual-bytes)
  stores actual bytes in Axon, creates content-addressed `file:bytes` nodes, and
  derives size and common hashes.

The baseline harness must run the same corpus through the applicable SCOT4,
Synapse, and Pivotglass paths. If a capability is commercial-only, unavailable,
or cannot be reproduced, the report must mark it **not measured** rather than
assuming parity.

## W-095-DOC-01 — Immutable intake

Create one Python-owned document envelope and lifecycle:

```text
received → validated → stored → parsed → extracted → awaiting review
         → admitted | partially admitted | rejected | failed
```

Every intake records:

- SHA-256 content identity, size, detected and supplied MIME type, filename,
  source URI or parent message, acquisition time, workspace, and operator;
- whether bytes were local, downloaded, received from SCOT, or referenced from
  Synapse;
- parser name/version/configuration, output digest, warnings, errors, skipped
  content, elapsed time, and resource limits;
- parent/child relationships for email parts, attachments, archive members,
  embedded images, and derived text; and
- access and data-handling labels supplied by the analyst or remote source.

Duplicate bytes reuse one immutable content object but create a new occurrence
record so each source, time, and chain of custody remains visible.

## W-095-DOC-02 — Safe parsing

Required formats by v0.9.5:

- UTF-8 and safely decoded plain text and Markdown;
- HTML with active content removed and original markup retained by hash;
- PDF text plus page boundaries and scanned-page OCR;
- CSV, JSON, and JSONL with row/object paths;
- RFC 5322 email, MIME bodies, headers, routing metadata, and attachments;
- DOCX, XLSX, and PPTX with document, sheet/slide, table, and cell coordinates;
- PNG, JPEG, and TIFF OCR when explicitly requested; and
- bounded RSS/Atom and analyst-approved URL retrieval.

Parsing runs locally by default in a constrained worker with byte, page, row,
member-count, expansion-ratio, CPU, memory, and wall-clock budgets. Macros,
scripts, external references, embedded executables, and active HTML never run.
Unsupported, malformed, encrypted, or truncated inputs produce explicit partial
or failed receipts; Pivotglass does not silently omit them.

## W-095-DOC-03 — Entity and occurrence extraction

The deterministic extraction authority begins with normalized cyber-relevant
types including:

- IPv4, IPv6, CIDR, domain, URL, email address, and message ID;
- MD5, SHA-1, SHA-256, SHA-512, SSDEEP, and TLS/JARM-like fingerprints;
- CVE, CWE, CAPEC, ATT&CK technique/sub-technique, campaign and malware names;
- filenames, paths, registry keys, mutexes, services, processes, user agents,
  UUID/CLSID/SID, certificates, ASN, and cryptocurrency addresses; and
- analyst-defined bounded match rules with previewed impact and explicit scope.

Each occurrence retains document ID, page/sheet/slide/message part, byte or
character span, row/object path when applicable, matched text, normalized value,
deobfuscation/refanging transform, surrounding context, extractor/rule version,
and warnings. The UI must jump from an entity to every exact source appearance
and back.

Entity resolution is deterministic where normalization is exact. Ambiguous
aliases, names, malware families, campaigns, organizations, and actors remain
review proposals. A common string does not become a common identity.

## W-095-DOC-04 — Model-assisted proposals

A configured model may propose additional entities, claims, relationships,
behaviors, contradictions, and information requirements only after local text
extraction. Each proposal must:

- cite one or more immutable source spans;
- include the exact prompt-template, provider/model, parameters, time, and
  response digest without exposing credentials;
- state the proposed type, normalization, rationale, alternatives, and known
  limitations;
- remain labeled `model-proposed` until an analyst accepts, revises, or rejects
  it; and
- be reproducible from an export that contains source spans and configuration,
  subject to provider determinism limits.

Document instructions such as “ignore previous directions” remain quoted
source text. They never enter the instruction portion of a model request.

## W-095-DOC-05 — Graph, gaps, and investigation flow

- Admitted entities become nodes only through the existing graph repository.
- The document, occurrence, and extraction receipt remain connected to each
  node so provenance survives normalization and deduplication.
- Co-occurrence is a document-location fact, not proof of an operational
  relationship. Any stronger edge requires an explicit rule, cited statement,
  or analyst judgment.
- Repeated entities and admitted edges may extend evidence clusters and
  longitudinal tracking, but never silently create actor attribution.
- Extracted ATT&CK references and behaviors feed the candidate-behavior review;
  unmapped behavior remains a framework gap.
- The Pursuit Brief surfaces unparsed documents, failed sections, unreviewed
  candidates, contradictions, missing corroboration, and high-value extraction
  gaps as next-action candidates.

## W-095-DOC-06 — SCOT4 and Synapse exchange

### SCOT4

- Import selected Dispatch, Intel, Product, Event, Entry, feed, and attachment
  content through a bounded preview with remote IDs and revisions.
- Preserve SCOT entity/flair occurrences and classes as sourced remote records;
  compare them with Pivotglass extraction rather than silently merging them.
- Publish only analyst-reviewed Pivotglass document summaries, admitted
  entities, source links, and extraction receipts through the existing
  approval/readback workflow.

### Vertex Synapse

- Map document bytes or references, hashes, parsed artifacts, occurrences,
  entities, and provenance to pinned Synapse forms and properties.
- Run ingestion in an isolated forked view with exact plan, budget,
  cancellation, before/after counts, conflict report, and reviewed merge.
- Use Synapse scraping results as a comparison source carrying rule and offset
  provenance, not as automatic local graph truth.
- At primary-backend cutover, retain one Pivotglass admission policy; Synapse
  storage must not create a second entity-resolution or relationship authority.

## W-095-DOC-07 — Analyst experience

The normal workflow is:

```text
drop, paste, select, or fetch
  → preview source and safety limits
  → parse and extract with visible progress
  → review highlighted entities, duplicates, conflicts, and gaps
  → admit selected evidence and proposals
  → pivot, cluster, compare, track, or report
```

The web and TUI commands must support single and batch intake, pause/cancel,
retry, source preview, exact occurrence navigation, filtering by type/status,
accept/reject with reason, and JSON/STIX/CSV export. Large collections use a
virtualized queue and bounded background workers. Nothing steals focus or
hides an error in the launch terminal.

## Match-or-exceed release gate

The v0.9.5 quality record must publish a versioned, non-sensitive evaluation
corpus containing clean, malformed, obfuscated, duplicated, scanned, structured,
and contradictory samples. It must report for every system and entity class:

- corpus coverage and formats actually tested;
- exact-match and normalized precision/recall/F1;
- source-location and round-trip provenance fidelity;
- duplicate/entity-resolution accuracy;
- relationship-proposal precision separately from entity extraction;
- processing time, memory high-water mark, and bounded-failure behavior;
- analyst corrections required and reasons; and
- unsupported, skipped, unavailable, or not-measured cases.

Pivotglass may claim **match or exceed** only when the pinned shared-corpus
results support that statement. Independent advantages required regardless of
raw extraction scores are complete source-span provenance, visible
contradictions, reviewable proposals, deterministic lifecycle receipts,
gap-aware workflow guidance, and no unreviewed graph mutation.

## Security and privacy release gate

- No parser process receives API keys or unrelated workspace secrets.
- URL retrieval blocks loopback, link-local, private, metadata-service, scheme
  confusion, redirect, and DNS-rebinding targets unless an explicit, separately
  threat-modeled local-source workflow authorizes them.
- Archive and compression expansion are bounded before materialization.
- Filenames and embedded paths cannot escape the content store.
- Rendered HTML and extracted text are escaped; formulas are neutralized in
  spreadsheet exports.
- Model submission is opt-in and shows exactly which source spans will leave
  the host.
- Originals, derived text, proposals, and accepted records have separate
  retention and deletion receipts.
- Fuzz, property, and seeded adversarial tests cover every parser and exchange
  boundary.
