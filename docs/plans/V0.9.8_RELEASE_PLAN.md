# Pivotglass v0.9.8 public release preparation

Date: 2026-09-27. Requested by the repository owner. Publication is complete only
after the immutable candidate is on public main, an annotated or signed matching
tag is public, all release assets exist, and their public bytes are verified.

## Scope and sequence

1. Preserve and inspect the current branch, including the already reviewed
   guided intake, graph/provenance, presentation, music, and Novice Q&A work.
2. Adopt `pivotglass` consistently for CLI, distribution, Python imports, plugin
   namespace, environment variables, runtime labels, and operator documentation.
   Offer explicit copy migration for existing local data; never overwrite a
   workspace or silently abandon it.
3. Use an AI editorial crew with experienced-analysis and newcomer-review roles.
   Check documentation against executable behavior, then build a navigable story,
   user guide, architecture, scientific process, SAT walkthrough, visualization
   examples, and analyst learning path. These reviews are not independent human
   endorsement or measured usability studies.
4. Organize repository navigation by audience and purpose. Retain dated release
   records; place large planning/decision history outside the root landing page.
   Preserve protected private design context and the separate nested project.
5. Run every Python and browser test; add tests for rename/migration, question
   review and authority, and documentation links/branding/navigation. Run lint,
   lock checks, production export, dependency audits, wheel/sdist builds, installed
   command tests, real browser interaction, and release-contract checks.
6. Record exact results and limitations in the qualification receipt. Generate
   SBOM, license inventory, and checksums from final immutable artifacts. Obtain
   the repository owner's release signature; do not substitute a new agent key.
7. Publish through a reviewable PR into main and a matching annotated tag. Attach
   all trust assets and verify the downloads and public commit/tag/release state.

## Branding and preservation boundaries

Active commands, imports, package names, settings, and current instructions use
Pivotglass. The legacy migration reader must recognize historical serialized
field prefixes to preserve old evidence. Dated historical
receipts use explicitly labeled placeholders for retired executable and
distribution names, preserving version, test, and publication facts without
pretending that old artifacts were built under the new names. Protected `storyboard/`,
`reckonings/UX-team.md`, and the separate `career-narrative/` project are outside
cleanup and publication. Protocol abbreviations unrelated to this product are
not renamed.

## Publication gates

- Full test and build receipts belong to the exact candidate tree.
- The configured `.githooks/pre-push` guard and release contract must pass.
- No external integration is claimed production-qualified solely from local
  fixtures. Missing live-system gates remain explicit.
- All downloadable assets must match SHA256SUMS; the owner's detached signature
  must verify. A missing owner-controlled signing key blocks final publication,
  not preparation of a reviewable candidate.
- `v1.0.0` requires the owner's approval after a separate final assurance pass.
